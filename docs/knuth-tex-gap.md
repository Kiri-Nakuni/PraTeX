# 素の TeX82 と Knuth TeX の差

対象: `claude1/tex82-perf`（`main` の `f174f44` から分岐、TeX82 互換のまま）
測定機: Intel Core i7-8650U、Linux、TeX Live 2026 の `tex` 3.141592653

## 測り方

この laptop は発熱で周波数が下がり、他 process（Electron 系）の負荷も乗る。
壁時計時間だけでは判定できないので、**`perf stat` の命令数を主指標**にする。
命令数は周波数にも他 process にも依存しない。実測のばらつきは 0.02% 程度である。

**起動固定費と組版スループットを分ける。** 本文量だけが違う文書（0, 1, 2, 5, 10, 20 本文）
を両 engine で走らせ、最小二乗で直線を当てる。切片が起動固定費、傾きが真の組版速度になる。
これを分けないと結論が逆になる。

- `tools/make-bench-docs.py` — 本文量の違う文書を作る
- `tools/bench-plain.py` — 両 engine を交互に走らせ、中央値と回帰を出す
- `tools/measure.py` — A/B 反復用。命令数と DVI の指紋だけを見る
- `tools/compare-dvi.py` — DVI を意味で比べる

## 出力の同一性

engine 名が `TeX` と `rtex` で長さが違うため、preamble の comment 長が 1 byte ずれ、
以降の byte 位置がすべてずれる。**クロスエンジンでの byte 一致は原理的に成立しない。**
そこで命令列を取り出し、位置依存の値（comment、`bop` の後方 pointer、`post` の pointer、
font の area）を正規化して比べる。

20 本文の文書で **DVI 命令 1,306,596 個がすべて一致した。** 同じ組版結果である。

なお rtex 対 rtex の A/B では byte 一致が成立するので、変更の判定にはそちらを使う。

## 出発点（`f174f44`）

| | 起動固定費 | 本文一つあたり |
|---|---|---|
| rtex | 47.4M 命令 / 6.6 ms | **72.96M 命令 / 13.4 ms** |
| Knuth TeX | 403.6M 命令 / 202.6 ms | **40.94M 命令 / 7.9 ms** |
| 比 | 0.117 / 0.032 | **1.782 / 1.681** |

**end-to-end では rtex が 2.35 倍速く見えるが、それは Knuth TeX の起動費のためである。**
Knuth TeX は kpathsea の経路展開と format 読み込みに 403M 命令・約 200 ms を使う。
rtex は kpathsea を持たず format を cwd から読むので 47M 命令・6.6 ms で済む。
この差は engine の速さではないので、比較から外す。

**組版そのものでは rtex が 1.78 倍の命令を使っていた。**

## 現在（`claude1/tex82-perf`）

| | 起動固定費 | 本文一つあたり |
|---|---|---|
| rtex | 44.0M 命令 / 6.1 ms | **62.83M 命令 / 8.5 ms** |
| Knuth TeX | 402.4M 命令 / 146.2 ms | **40.94M 命令 / 6.4 ms** |
| 比 | 0.109 / 0.042 | **1.535 / 1.334** |

命令数で 13.7% 減。傾きの比は命令 1.782 → 1.535、時間 1.681 → 1.334。

## 効いたもの

順に、素の `main` からの累計。すべて DVI byte 一致を確認している。

| 変更 | 単独 | 累計 |
|---|---|---|
| `panic = "abort"` | −2.35% | −2.35% |
| `codegen-units = 1` | −0.60% | −2.95% |
| lig/kern 表を hash から線形走査へ | −4.15% | −7.10% |
| 文字寸法の一括取得と `CharInfo` の縮小 | −0.37% | −7.47% |
| `round` から `f64::round` を外す | −0.41% | −7.81% |
| `update_last_node_info` の共通経路を書かない | −0.31% | −8.12% |
| 行ごとの節点列に容量を先に確保 | −3.20% | −11.32% |
| `split_adjust_material_off` の走査を先にする | −0.77% | −12.00% |
| 段落の節点列に容量を先に確保 | −0.74% | −12.74% |
| `hlist_out` に文字節点の内側経路 | −0.99% | −13.73% |

**一番効いたのは容量の先取り確保（合計 −3.9%）である。** `Node` は 80 byte あるので、
空の `Vec` から育てると再確保のたびに大量の複製が起きる。行と段落は最終的な長さが
分かっているか見積もれるので、先に確保するだけで malloc は profile 上 2.15% から
0.97% へ下がり、memmove は上位から消えた。

次に効いたのが lig/kern 表（−4.15%）。鍵は右側の文字一 byte だけなのに、文字対ごとに
SipHash を回していた。TeX82 は lig/kern 命令列を線形に走査する (573.)。

## 効かなかったもの

**節点を小さくすること。** `Node` は 80 byte で、`Noad` 80 と `DiscNode` 72 が枠を
決めている。大きい変種を `Box` に逃がせば 32 byte まで縮むが、`Node::X(...)` の
構築と分解が 260 箇所ある。

着手前に安価な実験をした。この作業負荷では作られない `UnsetNode` に 64 byte の
詰め物を入れ、`Node` を 80 から 128 へ 60% 大きくすると、命令数は **2.75% 増**えた。
逆向きに外挿すると 80 → 32 の縮小は **3〜5% 程度**にしかならない。260 箇所の改修に
見合わないので採らなかった。

**`target-cpu=native`。** 追加で −1.2% だが可搬性を失うので既定にはしない。

**インライン指示。** `FontInfo::dimensions` に `#[inline]` を付けると逆に 0.07% 悪化した。
LLVM の判断の方が良い。

## 残っている差

profile（命令数で重み付け、20 本文）は次のとおり。特定の関数に偏っておらず、
**全体が一様に 1.5 倍前後**である。

| 領域 | 割合 |
|---|---|
| main loop（`main_loop` `lookahead` `wrap_up` `move_right` `dimensions`） | 32.0% |
| 行分割（`try_break` `line_break` `create_new_active_nodes`） | 25.1% |
| 出力・DVI | 13.5% |
| 入力（`get_next` `main_control`） | 14.2% |
| 節点の破棄・malloc | 3.9% |

一様な差の出どころは構造的なものである。

1. **節点の表現。** TeX82 は `mem` 配列に 2 語（8 byte）の char node を置き、連結リストを
   pointer で繋ぐ。rtex は 80 byte の `Node` を `Vec` に持つ。行を作るときも頁に送るときも
   実体を複製する。TeX82 は pointer を繋ぎ替えるだけである。
   `line_break` の profile では、節点一つを複製する 10 命令の列が単独で全体の 5.5% を占める。
2. **境界検査。** `Vec` の添字は毎回検査される。safe Rust の範囲では消せない。
3. **列挙の判別子。** TeX82 は節点の型を 1 byte の欄で持ち、算術で分岐する。

1 を解消するには節点の保持を `mem` 配列相当へ作り替えることになる。これは PraTeX の
機能拡張と正面から衝突する（利用者判断で局所性は追わないと決めている）ので、
ここでは採らない。

したがって **1.1 倍という目標は、現在の節点表現のままでは届かない。**
到達には節点の保持方式そのものの作り替えが要る。現在地は時間比 1.334 である。
